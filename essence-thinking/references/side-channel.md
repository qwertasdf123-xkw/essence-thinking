# 旁路沉淀协议（不打断主线的思路跃迁）

本文定义"大任务执行中产生的分支思路如何被捕获而不打断主线"。当任务体量较大、思考中出现"也许还有更好的做法"类念头时读取；也作为 wiki 层 inbox 写入规则的补充。

## 目录

1. 设计本质
2. 捕获协议（思考中）
3. 分支条目格式
4. 处理时机（何时消费）
5. 与补丁/模式的关系
6. 无感知的量化标准

## 1. 设计本质

矛盾：新思路在**产生瞬间**价值最高（细节最全、动机最清晰），但论证它需要**切换上下文**，打断主线的流程状态。
- 解法 = 把两件事分离：**捕获**做成零决策动作（写一句就回主线），**处理**做成延迟批量（在天然停顿点统一消费）。
- 类比：OS 中断与 DPC（记录现场，延迟处理）、Kafka（生产与消费解耦）、Git stash（念头入栈，HEAD 不动）。
- 公理 4 的工程化："灵感来自思维过程"——如果捕获有摩擦，灵感就会丢；摩擦必须趋近于零。

## 2. 捕获协议（思考中）

触发信号（出现以下任一即捕获，不限时机）：
- "其实另一种做法可能更好…"
- "这个问题和刚才那个问题好像有共性…"
- "等等，这个前提真的成立吗…"（当前不展开验证，只记录疑点）
- 任何"以后值得研究"的念头

动作（硬性要求）：
1. 写**一句话**进 `.essence/wiki/inbox/`（≤2 行，含来源锚点），不展开论证——展开就是打断；
2. 立刻回到主线，不停顿、不评估价值（价值判断属于消费阶段）；
3. 捕获耗时预算：**≤20 秒**。超过说明在论证，立刻停止，把已写的半句留在那也成立。

## 3. 分支条目格式

```markdown
# <一句话念头>
- 类型：idea（新思路）/ patch（触及本体）/ question（待验证疑点）
- 来源：<主线任务名 + 当时的推理位置，如"设计 Network 段时">
- 锚点：<一句话：当时基于什么观察想到的>
```

示例：
```markdown
# 七段循环也许可以压缩成五段：Extract 和 Network 在小型任务里常合并
- 类型：patch
- 来源：skill 自优化主线 · Strip 段
- 锚点：连续三个小任务 Extract 产物只有一行，Network 直接引用
```

## 4. 处理时机（何时消费）

按优先级，命中即停：
1. **主线 Consolidate 段**：批量过一遍捕获的分支，逐条判：与当前结论相关 → 立即纳入辩证取舍；无关 → 留 inbox。
2. **主线 Evolve 段**：随 inbox 清空仪式一起处理（见 wiki.md §6）。
3. **用户主动要求**（"看看最近的念头"）→ 立即消费。
4. **inbox ≥20 条**：强制清空，不受主线状态限制。

处理即辩证取舍：不因为"是灵感"就照单全收，也不因为"偏离主线"就丢弃——按 wiki.md 清空仪式的三去向（进 moc / 归档 / 删除）执行；type=patch 的转 `.essence/patches/`（self-evolve.md 流程）。

## 5. 与补丁/模式的关系

```
分支捕获（inbox，原始念头）
  → 消费时论证成立 + 普适稳定 → 模式（patterns.md）
  → 消费时论证成立 + 触及本体 → 补丁提案（patches/）
  → 论证不成立 → 记录失效原因（同样是进化原料，公理 4）
```

念头不是结论：捕获时零判断，消费时全判断。两级分离正是"无感知"与"经得起推敲"的兼容点。

## 6. 无感知的量化标准

- 捕获动作 ≤20 秒、≤2 行；
- 主线恢复时间 ≤1 个思考步（写完立刻继续刚才在推理的句子）；
- 分支在 inbox 的存活期 ≤ 主线任务周期（任务内必须消费或明确留待清空仪式）。
满足三条，跃迁即为无感知；任一不满足，说明捕获协议被滥用（在思考而不是在记录），回到主线。
