# 无感知进化协议（skill 本体自我优化）

本文定义"思维结论如何安全地回流 skill 本体"。当 Evolve 段判断沉淀触及本体、或需要批量应用补丁时读取。

## 目录

1. 设计本质
2. 补丁生命周期
3. 提案格式
4. 应用规则（自动 vs 人工）
5. 版本纪律
6. 判定：什么值得进本体

## 1. 设计本质

无感知进化要解决的矛盾：**本体必须稳定**（协议不能每轮都变，否则不可预期）vs **本体必须进化**（沉淀的结论不回流，skill 永远停在发布那天）。
- 解法 = 把"改本体"从即时动作变成**提案队列 + 批量应用**：思考时只写提案，积累到阈值或用户发话时统一应用。
- 类比：数据库 migration 队列 / Linux 的 patchset 评审流程——快速记录，延迟合并，合并必有记录。
- 安全性来自分级：低风险类自动应用，协议类必须人工确认（公理 5：闭环里"谁来验证"不能缺）。

## 2. 补丁生命周期

```
思考中（Evolve 段）
  → 发现本体级结论 → et_log.py --patch "提案内容" 落盘 .essence/patches/<日期>.md
  → 积累（自然积累，或用户说"应用补丁"）
  → 应用：低风险类自动合并进本体文件；协议类逐条展示给用户确认
  → 记录：evolution.md 框架修订历史 + GitHub 提交 + 版本号递增
  → 清理：已应用的提案打 [applied] 标记，不删除（保留进化痕迹，公理 4）
```

## 3. 提案格式

```markdown
### PATCH-<日期>-<序号>｜类型：<协议类/低风险类>
- 来源：<任务/日志 slug>
- 现状：<本体当前的写法/缺陷>
- 提案：<改为什么 + 理由（含辩证取舍：优势/劣势）>
- 影响面：<触及哪些文件/流程>
- 状态：pending / applied / rejected
```

示例：

```markdown
### PATCH-2026-10-25-1｜类型：低风险类
- 来源：2026-10-25-arch-optimization
- 现状：routing.md 预算表"单任务总预算 ≤12k tok"为固定值
- 提案：标注为可在 context-guard 插件中按机型调整，并给出 8k/12k/16k 三档参考
- 影响面：references/routing.md 一处
- 状态：pending
```

## 4. 应用规则（自动 vs 人工）

| 类型 | 判定 | 应用方式 |
|---|---|---|
| **低风险类** | 不改流程语义：措辞、示例、模式条目、参考数值、错别字、格式 | 自动应用，应用后在 evolution.md 记一行 |
| **协议类** | 改七段流程顺序、增删公理/红线、改接口约定、改目录结构 | 逐条展示给用户，确认后应用 |

**任何补丁应用后必须跑一遍验证任务**（用本 skill 处理一个真实小任务），确认行为符合预期——应用即验证，验证即沉淀（闭环判据第四问）。

## 5. 版本纪律

- 本体每次变更 = 一次版本递增（0.0.1 级）；协议类变更 = 0.1 级。
- GitHub 同步：应用补丁后更新 VERSION 文件并提交；积累到值得发布时打 tag + release。
- 拒绝的提案记 `rejected` 并附一句理由——拒绝理由同样是进化原料。

## 6. 判定：什么值得进本体（进提案的标准）

同时满足：
1. **普适**：至少两个不同场景的任务得出同一结论；
2. **稳定**：验证强度按"推翻代价 × 新颖度"分级（见 meta.md 验证条）——继承旧思路的做论证链追溯（链上节点全部 active 即可）+ 抽样复核，全新结论做全量红队；各自验证级别下仍成立即可；
3. **关系可述**：能表述为"哪两个事物之间的什么关系"（公理 3）；
4. **改的是本体而非用一次就扔**：下次遇到同类任务，这条结论能省掉至少一步思考。

不满足的留在 patterns.md 当普通模式即可，不必升格为补丁。
